**Complete Product, UX, Architecture & Engineering Specification**

*Discover Bali. Respect Bali. Experience Bali.*

A production-oriented blueprint for direct import into an AI coding agent.

**Product type:** AI-powered connected tourism ecosystem for Bali: discovery, personalization, itinerary planning, booking, tickets, transport, guides, rentals, payments, live-trip assistance and responsible/culturally respectful tourism.

---

## 1. Executive Summary

Bali Experience AI is a connected tourism platform rather than a conventional OTA. It connects travellers with verified vendors, destinations, experiences, events, accommodation, guides, drivers, vehicles, tickets and transportation through a shared catalogue, booking layer and AI orchestration layer.

> **Technology must help travellers discover and experience Bali without encouraging behaviour that damages Balinese culture, sacred spaces, communities or the environment.**

North Star Metric: Completed Quality Bali Experiences per Active Traveller.

## 2. Product Vision

Become the digital gateway to Bali where a traveller can discover, plan, book, pay for and navigate a personalized Bali journey through one trusted ecosystem.

```
Traveller → Preferences → AI → Experiences → Itinerary → Booking → Payment
→ Driver/Guide/Transport → Live Trip → Experience → Review → Learning

Traveller ↕ AI Experience Engine ↕ Destination / Experience / Event / Hotel
↕ Guide / Driver / Vehicle / Ticket / Community ↕ Booking / Payment / Payout
↕ Cultural Governance / Responsible Tourism
```

## 3. Product Principles

- Personalized: adapt to explicit preferences and observed behaviour without silently changing explicit controls.
- Connected: products, vendors, destinations, events, transport and itinerary items share stable IDs.
- Transactional: discovery connects to real availability, pricing, booking and payment.
- Trustworthy: AI never invents availability, prices, events or cultural restrictions.
- Culturally respectful: cultural rules are first-class backend data and enforced before recommendations.
- Local-impact aware: experiences can expose sustainability/community attributes.
- Safe: routing, emergency information and live-trip features prioritize safety and consent.
- Scalable: modular monolith first; extract services only when justified.
- Observable: critical transactions and AI workflows have logs, metrics, traces and auditability.

## 11. Database Rules

- Use opaque UUID/CUID-style IDs.
- Use decimal/numeric for money and explicit currency.
- Store timestamps in UTC; display using destination/trip timezone.
- Use PostGIS for geographic operations.
- Unique provider webhook event IDs and idempotency keys.
- Soft-delete where history/audit matters; never destructively delete financial records.
- Keep inventory and payment state auditable.

## 25. AI Non-Negotiable Rules

- Never invent vendor, event, price, availability, ticket quota, booking confirmation, route facts or cultural restrictions.
- Never transact without explicit user confirmation.
- Retrieve first; LLM receives validated platform entities.
- Validate structured output with Zod/shared schemas.
- PROHIBITED entities cannot become actionable recommendations.
- Expose uncertainty instead of guessing.
- Explain recommendation reasons.

## 26. Recommendation Engine

```
score =
  preferenceMatch * 0.30
+ locationMatch * 0.15
+ budgetMatch * 0.15
+ availability * 0.10
+ rating * 0.10
+ culturalCompatibility * 0.10
+ sustainability * 0.05
+ localImpact * 0.05

1000 candidates
→ geo/active/verified
→ availability
→ budget
→ cultural validation
→ ~200
→ preference ranking
→ ~20
→ secondary AI re-ranking
→ top 5
```

Keep weights configurable. Candidate generation and ranking are separate services.

## 29. Responsible Tourism

- Local Impact Score: configurable 0–100 signal for local participation/contribution.
- Sustainability Score: configurable 0–100 score based on documented platform criteria.
- Crowd-aware alternatives when reliable crowd data exists.
- Geographic distribution to reduce concentration in a few tourism zones.
- Treat sacred/restricted locations differently from ordinary commercial attractions.
- Keep guidance concise, respectful and actionable.

## 34. Privacy & Consent

- Separate identity, travel, preference, location and payment-related data logically.
- Explicit location consent; background tracking is opt-in and justified.
- Store consent version/timestamp.
- Never store raw card data.
- Define retention/deletion policies before production.
- Least-privilege RBAC and audit privileged operations.
- Do not reuse precise location for unrelated personalization without appropriate consent.

## 35. Security

- HTTPS/TLS.
- JWT access/refresh strategy with rotation/revocation.
- RBAC and resource authorization.
- DTO/input validation and output validation.
- Rate limiting on auth, AI and costly endpoints.
- Secure headers/CORS.
- Secret manager/environment secrets.
- Signed webhooks.
- Idempotency keys.
- Audit logs.
- Secure media upload and private-by-default storage.

## 43. Coding Agent Operating Rules

- Read repository/docs before changes.
- Do not rewrite working code without reason.
- Prefer small domain changes.
- Maintain shared types.
- Avoid unnecessary dependencies.
- External providers must use adapters.
- Do not expose DB models directly as public API contracts.
- Do not give LLM unrestricted write access.
- All AI mutations pass application authorization/validation.
- Run lint/typecheck/tests after each milestone.
- Stop when critical acceptance criteria fail.

## 46. Critical Edge Cases

- Experience unavailable during payment → invalidate quote and offer alternatives.
- Price changes → require new confirmation.
- Payment succeeds but webhook delayed → remain pending until verified/reconciled.
- Duplicate webhook → idempotency prevents duplicate confirmation.
- Multi-vendor component fails → compensation/refund strategy.
- Driver cancellation → replacement matching and notification.
- Weather unsuitable → propose alternatives; never silently alter paid booking.
- Cultural rule changes → revalidate and notify.
- Connectivity loss → confirmed itinerary/tickets remain available offline.
- Location denied → app continues with graceful degradation.

## 49. Final Product Definition
